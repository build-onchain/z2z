## 1. Module decisions and implementation map

The native Rust workspace now has six host crates: the original five roles plus `crates/threshold`, the route-1a joint-note DKG/FROST primitive. Solidity/target contracts, guests and deferred SDK have separate builds. Core/node/SDK/contracts remain here; the user-owned sibling frontend is external; Zoss is independently developed. The active one-route release scope is owned by ARCHITECTURE §7.0 and roadmap R1–R10, which supersede older samechain-first/GUI-later descriptions below. A module is behavior, not automatically a process/repository; no mandatory company order DB or hosted backend follows.

The older five native roles are now **expanded core responsibilities**, not the complete product architecture with new lanes appended elsewhere: owner-local execution and exact-asset/action contracts span the same native base. Existing detailed [wallet](modules/wallet-authoring.md), [proof](modules/zcash-proofs.md), [destination](modules/destination-settlement.md) and [solver](modules/solver-operations.md) specs still own approved native behavior; [client SDK](modules/client-sdk.md) remains a later consumer. Samechain semantic relations/manual preflight and offline venue proposals now have scoped implementations; backed target execution and private matching remain unqualified, not implicitly implemented by those interfaces.

### 1.2 Core crate dependency map — acyclic

Arrow `A -> B` is the **intended responsibility dependency**, not a claim every import exists:

```text
runtime  -> protocol, zcash, proofs, chains, threshold
zcash    -> protocol when app contracts are needed + coherent upstream wallet/source primitives
proofs   -> protocol + coherent upstream consensus/crypto/proving primitives
chains   -> protocol when exact app/domain contracts are implemented + selected chain clients
threshold -> pinned FROST/RedPallas primitives; no wallet, RPC, storage or settlement
protocol -> no other core crate; pure rules/encoding, no network/storage/worker I/O
```

`runtime` now imports `threshold` for selected-peer DKG transport; `proofs` imports it only in development tests for the PCZT threshold-spend transcript. Neither dependency turns keygen into financial authority.

**Current manifest reality:** `runtime` imports `protocol`, `zcash`, `proofs`, `chains` and `threshold`; `chains` implements closed HyperCore testnet information reads and pure exact offline spot proposals using existing HTTP/JSON/amount dependencies, not a financial destination client or exchange sender. `proofs` imports `protocol`; `zcash` has no `protocol` dependency and consumes pinned upstream plus actual sibling `zoss-zcash`; `proofs` uses `zcash` and `threshold` only as dev dependencies. Actual owner review/signed preflight, ephemeral DKG and venue preparation remain distinct from unfinished signing/wrapped proving/settlement orchestration.

`zcash`, `proofs` and `chains` should not import each other's production implementations or `runtime`; callers compose siblings and canonical app contracts live in `protocol` only where needed. Guest/target-safe rules/encodings use the selected identical statement/version without pulling native wallets, workers, database, signer or RPC code into a verifier. Native and guest feature/dependency cohorts must stay coherent; no abstraction solely to forward one call.

**Wallet/local consumer seam:** owner-controlled caller composes source/chain data, `zcash` and `proofs`, storing U note/opening/authorization/payout witness locally. It is not required to run a solver service or Zoss message runtime. Solver caller receives only the complete agreed Q/redacted artifacts/scoped permitted witnesses. The native consumer composes these roles in existing runtime packaging as a goal, not an implemented general wallet SDK. Rust↔TS/WASM/FFI transport remains unselected/deferred; no duplicate protocol rules in future SDK.

## 4. Refund chỉ ước tính thời gian — quyết định đã duyệt

`RecoveryEstimate` remains a **conceptual observer output**, not a money predicate. Stages are source inclusion/history/finality → evidence/proving → target submission/finality → actual transfer, with overlap/scheduling reflected rather than double-counted. Heights/slots/time in different chains are not directly comparable or additive.

Required vocabulary is `status = Unmeasured | Estimated | EvidencePending`, `asOf`, stage, reason, measurement provenance, optional measured duration/range and assumptions. No measurements means no fabricated minutes/percentile/confidence. Stale inputs invalidate an estimate; passing ETA only updates status/reason, never authorizes refund, retires proof rights or guarantees completion. Chain halt, censorship, missing witness/artifact or source recovery lifetime can leave pending indefinitely; that is not independently terminal native delivery. Native client can show this without waiting for a TypeScript SDK.

## 5. Dependencies và version/repository discipline

### 5.1 Reuse, build targets and explicit implementation limits

Reuse actual upstream wallet/transaction/tree/node/consensus/crypto/proving implementations where they cover the selected relation. No replacement Orchard/Sapling/curve/node/proving-system project is selected. Correct historical consensus acceptance is not strengthened or changed by adopting modern-looking checks; authentic historical equations/parameters do not repair historical soundness. Proof relation/artifact owner is `proofs`; canonical app schema/rules owner is `protocol`; target proof validation/economic execution owner is the selected contracts; clients own exact call construction/state observations; runtime composes and persists. ### 5.2 Funded rule and artifact lifetime

Qualifying deployment rules must pin actual verifier/program/VK/schema, asset semantics, beneficiaries/fees and stable consumed domains. New version/SDK/Zoss release or messaging epoch/revocation does not retire them. ### 7.3 Evidence limits và internal artifact ownership

Tất cả **16 repo người dùng liệt kê** đã có primary-source role evidence ở bảng trên. Không build/test/run benchmark, dependency compatibility hoặc security audit. Supplemental GitHub API requests có access restrictions ở một số Zcash repos; không kết luận absent/archived từ fetch failure hoặc claim mọi repo active. No implementation/deploy/import license approval phát sinh từ role survey.

`crates/proofs` sở hữu circuit/witness/prover/verifier artifacts; `crates/protocol` sở hữu versioned rules/schema; chain contract packages sở hữu target verification và economic execution. Artifacts cần reproducible builds, license/upstream pin/security review và conformance evidence khi implementation được authorize; funded old orders giữ usable original proving/verification/recovery path. **DEX owns economic semantics**, không biến proof library thành quote/funding worker. Zoss independent release không retire settlement verifier. UI và Zoss external; core/SDK/contracts internal, không thêm SDK/contracts/proofs repos. 16 repo-role precedents trên giữ nguyên, không compatibility/build/security pass.
