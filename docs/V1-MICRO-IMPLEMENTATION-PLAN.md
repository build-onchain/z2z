## Global constraints

1. V1 is samechain, maker online, **fresh exact packet consent from both owners per fill**, CLI, P2P and full company-off recovery. Supported partial fills/proceeds/remainder are required; maker-offline standing authorization is V2.
2. No required company service, shared order database, paid VPS, paid/remote prover or witness upload. Independent peer/RPC/relay replacement must work. Zero paid infrastructure does not eliminate gas, local hardware, storage or electricity.
3. Existing SQL restrictions remain: PostgreSQL-only active SQL; **no local SQL execution**, Docker/Testcontainers/SQLite substitute or operational reset. Approved private URI plus isolated test scope is required; URI is not migration/reset permission.
4. Preserve old funded/signed bytes, encrypted custody, legacy journals/sidecars, ELF/VKey/PK/VK artifacts and migration identities. No blanket `target` cleanup, implicit migration, dual financial authority or funded-version retirement.
5. Proof-system/program/verifier changes require reviewed migration of all current callers and **new authority deployment**; existing authority has immutable verifier/program pins. Old rights remain usable under old rules/artifacts.
6. Inspect exact chain/deployment/runtime code/verifier/program/schema/assets/decimals before using observations. RPC observations remain `TRUSTED_NODE` at pinned canonical blocks, not independently validated consensus; missing history/reorg/unavailability fails closed.
7. Persist prepared intent/authorized bytes/reservations **before certificate export or transaction send**. Releasing a valid owner certificate authorizes that exact role/packet for permissionless execution when paired with the other valid role; once both are available, anyone may call `Authority.fill` while onchain eligibility/expiry permits. Peer ACK, local abort, disconnect and negotiation timeout do not revoke released authority. Keep released bytes/locks and conservative `Released/Submitted/Unknown` until actual signed expiry is authenticated under the selected chain policy or competing consumption is **finalized and reconciled**; an unfinalized cancel/receipt cannot safely unlock. `Completed` requires actual correct transfer and finality; stale backups never resurrect spent rights.
8. Verify both proofs, consume unique rights, append complete recovery outputs and transfer assets atomically. Invalid proof, receiver/token failure or race must roll back all attempted effects and retain only genuinely eligible retry rights.
9. Secrets never enter peer frames, SQL, argv, logs, artifacts committed to the repo or remote prover requests. Production secret-bearing recovery behavior has an explicit approval hold; generated-key checks do not waive it. File deletion is not an erasure-complete claim.
10. No deployment **including local Anvil**, signing/submission, fund movement, production-secret consumption, operational migration, mainnet action or git push is authorized by this plan. Transaction approval must show chain, signer/fee payer, recipients, assets/raw amounts, fees and simulation result.
11. Strict GD2/privacy blockers remain; public advertisements are not implicitly private or independently backed. No disclosure-only waiver or reduced acceptance is assumed. If the required privacy/backing construction remains unavailable, the affected release task stays blocked while permitted nonfinancial work proceeds.
12. Existing source pins beat stale documentation. `SamechainAuthority.sol` and `foundry.toml` pin **Solidity 0.8.34 / Cancun** (testnet prose is already corrected). P0.03/P5.01 qualify the compiler per EVM lane; there is no downgrade.
13. Owner Phase 0 answers (2026-10-06) are binding inputs and are recorded in the [integration report §2](research/2026-10-06-phase0-coverage-invariants.md):
    - bilateral-counterparty-only disclosure, with no GD2 waiver;
    - direct connections plus an optional independent relay;
    - a per-owner PostgreSQL design;
    - verified offline backup before funding and before each new release capability;
    - packet order: descriptors → freeze → backup/read-back → consent;
    - Native plus a new fixed-supply 6-decimal constructor-only token;
    - two-operator agreement on a common finalized hash (an owner-run non-validating node is allowed as the second source, design only);
    - resource methodology only;
    - a ≤15 min provisional proof objective;
    - an immutable authority on every lane.

## Review focus

- **Ambiguous or hostile discovery claims:** authenticated advertising is not ownership/backing/spentness proof; P0.05 and P2.17 reject misleading verified labels and substituted domain/amounts.
- **Owner secrets across async/network boundaries:** malformed or canceled negotiations, crashed/OOM workers and scanner diagnostics must not disclose witnesses; P1.11–P1.15, P2.21–P2.23, P3.03–P3.05 and P4.07 own the checks. Exact packet assembly exchanges public encrypted-output descriptors only, never openings, keys or witnesses.
- **Crash after certificate release/sign/send, stale backup or duplicate operation:** persist released bytes and locks before export; keep `Released/Unknown` until chain reconciliation. P3.08 explicitly exercises late permissionless execution after abort/timeout; P2.05–P2.06, P3.20–P3.22 and P4.09/P4.16 prevent premature unlock or revived rights.
- **First proof valid, second invalid or later transfer fails:** no partial nullifier/tree/payment effects; P3.17–P3.20 prove rollback and valid retry.
- **Company disappears before recovery:** old artifacts, complete ciphertext history, current consumption and gas must remain independently usable; P4.04–P4.18 and P5.09 own the drill.

## Tools, permissions and estimate convention

All task references below are links into this document or the source map. `None` means no task dependency, not no constraints. Every task inherits the global constraints.

**Dependency semantics:** code/funded/release tasks require successful acceptance of their prerequisites. Benchmark-analysis/alternative-decision tasks may consume a recorded failed run and its measurements (P1.18–P1.21); this never treats failure as proof qualification. A selected alternative must repeat every baseline relation/privacy/measurement/target check before P1.23 can close. Where a task references another phase, follow that edge rather than waiting for all lower-numbered phases.

Creation is the exception: it prepares/proves a new note **before** admission. P4.01–P4.05 uses existing tree/decrypt/prover/call-builder primitives directly with that controlled corpus, not P3.09/P3.10 or a future live scanner. **P4.11 actual deployed-context restore** uses fresh creation secrets/backup, actual deployment pins and a genuine creation proof before funding; it must not depend on P3.13 or an existing note path. **P4.12–P4.18 actual funded recovery** consumes P3.13/P3.15 history and cannot close on fixture or pre-deposit evidence.
