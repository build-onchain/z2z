## Parallel tracks and preregistered go/no-go

- **Build:** One base mint and quote mint, hackathon MVP bounds **≤8 user orders per epoch, 1 maker, 1 level per side**, with **per-epoch isolated PDA-owned base and quote vaults**. These are provisional scope limits, not measured capacity; the scale targets of 64 orders and 8 levels/side × 4 makers require LiteSVM/SBF CU and transaction-size benchmarking before adoption. On-chain primary `p* = round_half_even((p_lo+p_hi)/2)` computed by the program over the contiguous maximizing integer-tick interval (`p_lo` submitted ask limit, `p_hi` submitted bid limit); no cross if `V*=0` or a side is empty. Limit eligibility, price priority then marginal pro-rata/tie-break, escrow and aggregate-order fee settlement, independent optional maker residual after primary. `settle_order`/`settle_maker` are permissionless only after `Cleared`; `refund` is permissionless only in `RefundOnly`, never after `Cleared`; transfers remain **conditional on issuer/token-program permission**. Each settle/refund instruction pays at most one recipient leg; settlement spans transactions. Program verifies any sort hint. See [mechanism](../mechanism/01-MECHANISM-SPEC.md) and [program design](../architecture/04-ONCHAIN-PROGRAM-DESIGN.md).
- **Reference trading-UX app** ([ADR-011](16-ROADMAP-AND-DECISIONS.md#adr-011--reference-trading-ux-app-with-off-chain-routing-layer), proposed): thin app on the SDK with order form, epoch countdown, cancel while Open, CROSS/RESIDUAL receipt, settle/refund buttons, a limit suggestion from an immediate external quote where available, and an optional **second wallet-signed** fallback trade for the refunded remainder after settlement. Route comparisons show only `OBSERVED_EXECUTABLE`/`OBSERVED_INDICATIVE`/`UNAVAILABLE`. SYNTHETIC mints only; no atomic fallback, no maker bridge, no aggregator or savings claim. Cut this before any core-mechanism path if time runs short.
- **Validation:** Initial target is *eligible distributors with a repeated tokenized-stock execution job*, plus makers for residual-indication discovery. Interview directly and collect documentary order-timing examples where allowed; never manufacture trading data or present intent as live orders. Pre-register before counting outcomes: **≥10 direct conversations; ≥3 independent concrete examples of repeated opposite-side flow in the identical mint and time window; ≥2 distributor trial tickets; one written, nonbinding maker residual indication; ≥3 paired windows of executable alternatives in which both buyer and seller improve net after fee, network cost and latency.** These are *thresholds to test*, not evidence attained. See [GTM/validation](../business/12-GTM-AND-VALIDATION.md); E17 and E18 remain U.
- **Decision:** If same-mint overlap, maker appetite, bilateral all-in improvement or legally qualified asset/participant route cannot be demonstrated, **kill the live-market thesis or pivot only by an explicit decision record**. A synthetic engineering success cannot flip a commercial failure into a GO. The validation plan contains the evidence-collection details and stop rules.

## Demo definition of done, with explicit fallback

A **technical-complete SYNTHETIC demonstration** requires an independently reproducible localnet run (devnet only if available and authorized) showing the provisional MVP bounds **≤8 user orders/epoch, 1 maker, 1 level/side**: one fictitious Token-2022 base mint and test USDC quote under their *separately recorded* token programs and **per-epoch PDA-owned vaults**; one bid and ask fully pre-funded; close and program-computed cross price/priority/pro-rata; immutable primary result and fixed entitlement ledger backed by intact vault balances; permissionless bounded settlement with **one recipient leg per instruction** and **one** proposed 5-bps fee **per user order on aggregate CROSS + RESIDUAL filled notional `N`**, `ceil(5N/10_000)`; buyer pays `N + fee`, seller receives `N − fee`; protocol/distributor/crank 6/3/1 shares are each floored and remainder is fee-vault dust. A CROSS has two charged user sides (≈10 bps of cross notional), a RESIDUAL has one (≈5 bps of residual notional), maker zero. Show optional fully funded maker residual with distinct **RESIDUAL** receipt price where needed, a no-maker path, missed-clear-deadline **pre-clear** RefundOnly and withdrawal of original deposit *only where token transfers permit*, and a pre-clear issuer guard refusal. After `Cleared`, show **per-leg SettlementBlocked** preflight succeeding without transfer with reason code and preserved entitlement, then permissionless retry after removing the test block, not post-clear RefundOnly. Unexpected transfer CPI failure reverts and is surfaced off-chain; there is no `mark_settlement_blocked` instruction. V1 market creation must refuse **any mint with a permanent delegate**. In a separately labelled adversarial SYNTHETIC shortfall scenario, check vault balance against outstanding leg entitlements, emit `VaultShortfall`, mark the leg `Impaired`, stop all its payouts and preserve nominal claims unchanged (pre-clear claims equal original deposits) while the unaffected leg continues settling. No automatic redistribution, restitution or recovery path is part of Kerb. All instructions/receipts must reflect actual run results, not a static UI script. A frozen issuer vault or impaired leg can keep claims unpaid indefinitely or unrecoverable; disclose this without a promised recovery date.

A **submission-ready presentation** additionally requires live-playable ≤3-minute video (prefer Loom), ≤10 phone-legible slides with ≤20 words apiece, verified team attribution or explicit missing evidence, traceable synthetic code, public repo/license with reproductions, clear competitor and legal caveats, and honest validation status. The deck/script in [13](../pitch/13-PITCH-NARRATIVE.md) is not proof of these outputs. If one acceptance path fails, downgrade claims to what actually runs rather than insert a mock, fake receipt, fixture labeled as user traffic, or alleged devnet deployment.
