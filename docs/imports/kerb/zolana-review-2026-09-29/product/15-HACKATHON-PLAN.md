## D0 boundary, deliberately narrower than R1

**[I]** D0 consumes a **fixed-size synthetic order corpus** for a named synthetic Solana asset and simulated Ironwood-ZEC price/quantity denomination; the settlement ledger is a model only. Do not mint/fund SPL, generate deposit instructions or addresses, spend or scan live ZEC, connect real wallets, send RPC transactions, simulate a real customer balance as paid, or represent a local mock as a testnet venue. The three future **distinct** candidate pairs are (A) SYNTHETIC SPL ↔ **testnet** Ironwood ZEC in separately authorized later research, (B) canonical Solana USDC ↔ native Ironwood ZEC, (C) one exact qualified Solana xStock mint ↔ native Ironwood ZEC. D0 funds **none**. There is no qualified xStock. [Pair market assessment](../business/10-MARKET-AND-COMPETITION.md) and [roadmap](16-ROADMAP-AND-DECISIONS.md) do not turn D0 into R1.

The owner requires that no single matching operator/control domain learns **plaintext order or identity linked to an accepted order**. Encryption or an MPC demo might protect order content under particular assumptions but does **not** itself solve ingress, RPC, Solana signer, funding account, credential redemption, common-control logs or custody/eligibility-access linkage. A matcher joining an accepted synthetic order to a simulated participant fails the gate. Actual independent cluster control is a separate question. Distinct custody/eligibility actors may possess privileged identities and payment views; public Solana metadata can remain visible. D0 must **show failures honestly**, not claim global anonymity. [Arcium encryption/protocol/governance documentation](https://docs.arcium.com/developers/encryption), [MPC protocols](https://docs.arcium.com/multi-party-execution-environments-mxes/mpc-protocols), [cluster governance](https://docs.arcium.com/clusters/permissioned-clusters) and [limits](https://docs.arcium.com/developers/limitations) **[P]** describe possible technology, not a selected working Kerb cluster.

## Concrete artifacts to build only inside approved D0 scope [I]

1. **Versioned rules and corpus:** fixed pair/network domain, synthetic identities segregated from order attributes, epoch cutoff, integer lots/zatoshis and limit bounds, explicit rule hash, expiry/nonces, valid/crossing/uncrossed and rejected examples, deterministic seed and expected outcome specification. Prohibit real addresses/keys or captured user orders. Snapshot accepted/rejected records and public outputs with reproducibility instructions.
2. **Reference auction and accepted-set checks:** a deterministic *local reference* computes unique accepted ciphertext-set identifier, full-set availability checks, one-use synthetic funding eligibility tokens (clearly simulated, **not** a real unlinkable funding credential), integer clearing/tie-break, per-order sealed-fill representation, no overfill, limit adherence and asset conservation. A signature or Merkle root alone does not prove omitted pre-acceptance orders were included; show exclusion/late-arrival/duplicate/replay abort cases. Prove only tested arithmetic/invariants; no claim of on-chain escrow or order privacy from a plaintext engine.
3. **MPC run only if honestly available:** if an actual independently governed matching cluster, permission and usable circuit are available, supply the **same** fixed corpus under client encryption, record operators' real control domains and limits, compare outputs with reference, reproduce abort and demonstrate whether any single node sees content. If unavailable, explicitly label “MPC unavailable; plaintext reference only” and **do not** generate a scripted mock API pretending to be deployed MPC. Even a successful cluster run does not prove identity unlinkability or funded-set integrity.
4. **Adversarial observer-by-observer leakage trace:** for each accepted synthetic order build synthetic RPC/IP/timing, public Solana signer/account/mint/amount, intake receipts, funding-credential redemption, and any eligibility/custody record the same matcher/operator could access; test unique amounts, reused accounts, timestamps and log correlation. For each observer (single matcher + its shared control domain, chain observer, independently governed eligibility actor, scanner, threshold spend signer, colluding combinations) record fields, attempted linkage, success/failure, and **why**. The matcher-specific identity gate fails on one mapping even if content remains encrypted. Synthetic traces do not prove deployment's network metadata cannot leak.
5. **Non-settling failure-state model:** represent distinct buyer-ZEC deposit and seller-SPL lock in *simulated state only*, including no/one/both hypothetical legs funded, admitted/aborted, authorized ≠ paid, ZEC-first then SPL fails, SPL-first then ZEC withheld, duplicates/wrong pair/stale nonce, reorg, frozen SPL, offline/colluding custody quorum, dispute and separate conditional refund branches. No “transaction success” banner; label every transition simulation. Committee-signature validity is not Ironwood effect proof; threshold custody cannot force a ZEC refund. See [security test plan](../security/08-TEST-AND-VERIFICATION-PLAN.md).
6. **Review package:** executable command and input/output transcript *if an implementation is produced*, assumptions/control-domain map, pass/fail matrix including negative cases, exact scope disclaimer, cost/business unknowns, competitor citations and a claim ledger tied to [pitch audit](../pitch/14-JUDGE-RED-FLAG-AUDIT.md). If only documents exist at a checkpoint, report **documents only** and list unavailable runtime proof, not substitute screenshots or invented transcripts.

## Stop rules and subsequent decision [I]

At any point, stop “privacy-success” framing if a single matcher/control domain learns identity linked to an accepted order or plaintext content; pause implementation claims if accepted-set omissions, duplicate synthetic credits, wrong pair/replay, nonconservation or divergence from reference occur. If no real cluster, label only a reference simulation; if no executable surface, label document design only. If no two-sided need emerges under [discovery gates](../business/12-GTM-AND-VALIDATION.md), stop the commercial pair thesis even if D0 arithmetic works. A substantive R1 proposal **must** separately specify a real privately binding single-use funded credential, independent matching and custody roster/key shares, Zcash scanner/confirmation/reorg policy, Solana escrow code/security review, verified matcher identity unlinkability, incident/loss allocation, jurisdiction/issuer approvals and explicit owner authorization for any testnet transaction. R2/R3 with actual USDC/xStock introduce additional real-asset gates. D0 passing alone advances **none** of these authorizations.
