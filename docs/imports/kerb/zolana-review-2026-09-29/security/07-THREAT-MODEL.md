# Kerb Zolana — proposed threat model

**Status: owner-review draft, 2026-09-29.** This models an unimplemented, unaudited Solana↔Zcash market candidate, not a deployed control set. [The design spec](../../docs/docs/superpowers/specs/2026-09-29-kerb-zolana-design.md) is itself proposed; these staging docs do not replace the active legacy docs or authorize funding, signing, deployment, testnet transfers or real-asset activity. [I] means design inference/requirement, [P] means a source's directly stated protocol/vendor description, and [U] means unverified. Source retrieval date is 2026-09-29 unless noted. A vendor claim is not an independent audit. Evidence and attack scripts are specified in the [verification plan](08-TEST-AND-VERIFICATION-PLAN.md); none is reported passed.

**Current-authority banner 2026-10-01:** retain this staged threat model as history; [Kerb current authority](../../docs/00-CANONICAL.md#0-current-documentation-authority) adopts shared Zoss source/context/domain/Solana libraries in Kerb-controlled processes **docs only**. No mandatory added viewer/IVK handoff/shared key or witness/cache/log daemon, watchers/receipt/quorum. Kerb claimant/ownership/canonical/inventory/durable dedup still gate credit; FAA/MPC/ledger/FROST/payout/refund/recovery remain app-owned. Optional messaging stays OFF/non-money; the financial/private candidate remains unapproved and **GD2 structural FAIL**. No runtime/privacy pass or duplicated Zoss core gate register follows.

**Later owner-review candidate:** [integrated production-demo design · 2026-10-01](../../docs/docs/superpowers/specs/2026-10-01-kerb-production-demo-design.md) selects one complete workflow while this Sep29 draft preserves unapproved history. Neither is authoritative/frozen/production-ready; no implementation, actual independent operator roster, privacy proof or build/deploy/funds/publication/legacy cutover approval follows. New selections: FAA privileged full-order+identity view outside matchers, symmetric PREPARE holds, canonical epoch fences, sealed prices/results, unanimous business decisions with 2-of-3 spends, SPL-first. Historical D0 researcher-only arithmetic is not the funded workflow or a default public-price policy.

**KNOWN structural privacy failure (§6/GD2 of linked later candidate):** allowed padded8 with one natural seller Alice and attacker-owned contra orders reveals accepted identity through public epoch escrow. If her ask is known6 or10, legitimate attacker buy8 fills iff6, revealing private limit. Own-result inference is inside attacker view; no MPC compromise required. GD2 **fails** this permitted corpus, not merely U/unmeasured. No currently viable private production-demo release satisfies unchanged requirement. Padding/private price/FAA isolation cannot waive it; hidden collateral/membership with compositional evidence or explicit owner-reviewed guarantee change required, none approved.

**Other exact safeguards remain proposed, not executed:** primary spec separates `Rct` ciphertext provenance, `Cholds` private prepared-membership opening and `Corder` certified plaintext relation; pins coordinator whole-book owner/version and each FAA-certified client result key. `AllocationActive` (exact finalized FINAL + complete authenticated chunks + unanimous acknowledgement + fully applied journal) gates BOTH unused refunds and Release. `SellerPayout` needs SPLReleased; `BuyerRefund` needs returnable disjoint entitlement, not SPL delivery. Entity-scoped IDs, cutoff/expiry consistency and non-rollback signer/journal restore prevent replay/recreated availability. None remedies the known §6 structural privacy failure.

## 1. System, assets and non-goals

**Owner-selected scope:** one architecture across Solana and Zcash, with *three isolated markets*: SYNTHETIC Solana SPL token/Ironwood Zcash testnet ZEC (only after a separately authorized R1 experiment); canonical Solana USDC/native Ironwood ZEC; and one exact, issuer-qualified xStock mint/native Ironwood ZEC. The latter two are research candidates, not listings. A market identifier must bind chain/cluster, exact SPL mint **and token program**, Zcash network/pool and pair/epoch/rules; tickers and cross-chain representations are not fungible. The owner accepted threshold-committee custody of shielded ZEC and the resulting non-atomic and non-unilateral-refund trust model, **not** a live launch or a weakening of the independent matcher-privacy requirement. See [architecture](../architecture/03-SYSTEM-ARCHITECTURE.md) and [decision record](../product/16-ROADMAP-AND-DECISIONS.md). [I]

Protected assets: (A1) trader order contents—side, limit, quantity, destinations—and the identity linked to each **accepted** order; (A2) accepted-ciphertext set, funding eligibility, auction correctness and availability; (A3) exact SPL escrow and ownership/claim entitlement; (A4) ZEC notes under committee spend control and the per-pair deposit-credit/liability ledger; (A5) signer shares, incoming viewing capabilities, transaction witnesses, personal/legal-eligibility records and private audit mappings; (A6) settlement attestations, nonce/state transitions, incident and recovery evidence. Threat outcomes include information disclosure, exclusion or manipulation of accepted orders, fabricated credit, asset substitution, double release, theft, censorship, permanent lock or unallocated non-atomic loss. [I]

**Not protected:** global anonymity; confidentiality against independently governed **FAA seeing full order+identity** or custodians/coordinator seeing privileged settlement data; guaranteed execution/fair price/ZEC refund or atomic exchange. FAA is an explicit later design alternative, **not implemented blind credentials**; actual control/access/log/recovery separation from every matcher is a hard gate. Public SPL accounts/signers/amounts/timing [P: [transaction structure](https://solana.com/docs/core/transactions/transaction-structure), [token transfers](https://solana.com/docs/tokens/basics/transfer-tokens)] and custody/viewing/network metadata can still defeat matcher privacy. Later candidate selects **no default public clearing price**; participant own price and coordinator allocation sealed, yet auxiliary-output attacks remain. Ironwood native network/pool scoping required [P: [ZIP258](https://zips.z.cash/zip-0258)]; [ZIP203](https://zips.z.cash/zip-0203) expiry only rejects unmined transaction, never refunds mined deposit.

## 2. Boundaries, attackers and privileges

```
TRADER/CLIENT --full signed order--> independent FAA (privileged order+identity)
    |--encrypted SAME certified tuple--> separate intake/availability --> MPC
    |--SPL lock/prepare-----------> Solana escrow --> epoch COMMIT/FINAL/ABORT fence
    |--shielded deposit---------> scanner/IVK --> unique private credit + FULL max-debit prepare
    |                             independent buyer journal; held during matching
                             |                                | spend coordinator/prover
   accepted ciphertext/funded-set evidence --> MPC matchers --> sealed fills --> coordinator
                                                              |--custody signing quorum--> Ironwood payout/refund
                                                              +--Solana authorization--> escrow

   Zoss v1 branch: RESEARCH-ONLY, DISABLED FOR FUNDED KERB. Same receiver AND same note
   would permit optional positive-receive notification, not credit, payout or refund proof.
```

| Boundary / compromise | Attacker capability and required containment [I] | Test |
|---|---|---|
| Malicious client and external byte inputs | Submit wrong chain/mint/program/pool, overflow quantities/prices, reused signature/nonce, ambiguous destination, duplicate deposit reference or forged credential; order signed over exact domain/rules/expiry and valid one-time funding eligibility. Client secrets/viewing keys never sent to intake. | T03–T06, T10 |
| **Single matcher/control domain** | One matching operator plus every intake, RPC, transport, eligibility, custody service, telemetry or log it controls or *can access*. May be malicious and join ciphertext/receipt to signer, IP, redemption, chain events or shared database, or withhold input; must learn neither plaintext order nor **identity linked to an accepted order**. Multiple servers under one admin are one adversary, not independent MPC members. This remains **unmet**. | T01–T04, T07 |
| Independent eligibility + FAA | Later FAA sees full order+identity, verifies ownership and exact durable funding hold, certifies SAME tuple inside MPC. May deny/forge/leak; actual separate admin/ACL/log/export/recovery/support governance is hard gate, not nominal labels or implemented blind credentials. | T02, T03, T15; parent PD04/GD2 |
| Separate intake/admission/availability | May censor before receipt, leak request→slot/identity metadata or equivocate/omit accepted slots. Exact certificate/hold generation, prepared hold evidence and canonical immutable root required; abort/unknown commit never frees funds without irreversible canonical fence. | T04, T07; parent PD01–PD02 |
| MPC cluster | Later Cerberus/distributed preprocessing proposed, not observed config/independence. | Kerb scanner/IVK and custody coordinator | Scanner alone confirms correct Ironwood receiver, note, amount, network and confirmation policy before one credit. Separate from matcher access. | T05, T09–T11 |
| Threshold ZEC spend signers | Quorum can sign a wrong recipient/amount, withhold, collude, reuse shares or lose quorum; each signer must inspect effects and recompute/check sighash from authenticated confidential transaction details, not blindly sign a hash. | Solana escrow/program and upgrade authority | Unauthorized account metas, PDA seed collisions, wrong token program, arithmetic/fee errors, stale signer roster, invalid quorum transition, replay, double claim, malicious upgrade, vault frozen/shortfall; program must check exact state, owner/discriminator, signer/writable constraints, exact mint/program, vault entitlement, nonce/expiry and threshold/version. No program or deployed address exists yet. | T05–T06, T10, T12–T15 |
| Public/RPC/issuer and two chain observers | May reorder/censor requests, correlate amounts/times, fork/reorg Zcash or Solana, and exercise issuer freeze/pause/delegate/extension authority. Public chain cannot attest private recipient by reading a Zcash txid. Freeze can permanently defeat an SPL transfer even if a program allows it. | T01–T02, T10–T15 |
| Zoss optional message watchers, relayer, endpoint (disabled critical path) | **Message-profile history only, not overall shared-core scope:** same-receiver/same-note non-money diagnosis has no ownership/credit/unspent/hold/accepted-root/payout/absence/refund/reverse proof. Retained Sep30 opaque receipt has random delivery_id, route/context/app key+nonce/public fields/ciphertext digest, no default locator/height/value/full memo/private-record hash; these stay in private signed provenance. PreSep30 cmx-derived ID/height/value/envelope defaults are rejected history. Timing, stable keys, viewing maps and shared access still threaten privacy. The **message runtime** disconnected never changes money state; native library consumers are a separate Kerb-owned direction in the banner. [Current consumer](../../../../../../zoss/docs/kerb.md), [core](../../../../../../zoss/docs/ARCHITECTURE.md), not privacy/funding proof. | T01–T02, T16; parent PD11/GD7 |

**Trust is not transitive.** A valid Solana quorum signature proves which keys signed a proposition, not that the recipient received Ironwood ZEC. A mined Zcash transaction/txid or a Zoss `Delivered` event proves neither the proposed beneficiary nor a private note's payment effect to the Solana program without separately specified proof and finality. Signer-controlled payment is a custody promise, not a cryptographic condition on the Ironwood note. [I]

## 3. Observer leakage and control matrix

`Known` = actor can access by role/design; `Possible` = plausible via public traces/logs or shared rights, to be experimentally evaluated; `No claim` = absence of a justified confidentiality guarantee, *not* a security proof. Columns distinguish **individual matcher** from an independently governed custodian. No field in this table licenses combining those roles under one operator. [I except cited chain/vendor facts]

| Observer | Order content / accepted-order identity | Funding, settlement and correlation data visible or accessible | Control / residual risk |
|---|---|---|---|
| Trader and wallet | Own plaintext/signature/identity; may see only own sealed fill. | Own Solana signer/accounts and ZEC destination/transaction; wallet/RPC leak IP and timing. | May submit false data, reuse credentials or leak own metadata; cannot create extra entitlement. |
| Single matcher **including accessible services/logs** | Intended no plaintext or accepted order→identity join. FAA/custody/intake/admin/recovery/public-chain access graph untested; encryption alone insufficient. | Public SPL amounts/signers/timing, intake maps, shared cert/funding logs, keys and settlement outputs can identify orders. | Censor/abort/infer; **no default public exact price**, but any content/identity recovery fails funded gate. |
| Independent eligibility + FAA | **Full order, identity, eligibility, client wallet authorization and funding hold known** in later candidate. | Private exact order/certificate/credit/escrow/refund relation stays outside all matcher-accessible exports/admin/support. | Deny/forge/leak; real independent governance and exact hidden certificate/client verifier remain hard gates. |
| Separate intake/availability | Encrypted slots/certificates, arrival metadata/receipt/root; request→slot map may identify participants. | Fixed eight slots, certified padding/shared payer proposed, not proof against active timing/output/funding attacks. | Censor/equivocate; root not proof against pre-receipt censorship; missing inputs preserve holds. |
| Custody scanner / IVK holder | No matching plaintext required; **does** see note receiver/value/memo/reference/height for its monitored pair, possibly client identity via separate KYC. | Private `cmx`, tx/note, confirmations, credit→accepted-order and payout mappings if assigned. | Can issue false credit or leak mapping; IVK is not spend key. Govern viewing and spend separately. |
| Custody transaction constructor/prover and quorum signers | Need sufficient payout data to approve recipient, amount and sighash; may know order-to-payment mapping depending on workflow. [ZIP 312](https://zips.z.cash/zip-0312#threat-model) [P, draft] treats these as privacy-privileged. | Witnesses, private payment effects, sign approvals, per-pair liabilities. | May freeze/misdirect ZEC or leak payment history; threshold does not conceal from each signer by default. |
| Solana public / block producer / RPC | Encrypted-order plaintext should not be published; **no global anonymity claim** for signer/funder or accepted order if account/receipt exposed. | [Solana tx format](https://solana.com/docs/core/transactions/transaction-structure) [P] reveals signatures, accounts and instruction data; token account amounts/recipient and timing are observable. Clearing price if chosen public leaks market aggregate. | Front-run/censor/reorder, correlate unique amount/time, inspect Solana-facing attestation; fees and account identities remain public. |
| Zcash public / node / network peer | Ironwood note recipient/value shielded by protocol design, but chain time, fee, pool balances and client network metadata may correlate with Solana. | Custody payout effect not publicly readable just from a txid; reorg can revoke prior provisional confirmation. | Censor or delay; cannot compel custodians to refund. |
| Zoss watcher/relayer/public endpoint **if diagnostic enabled** | Watcher sees private note/memo/value/height/occurrence; public sees CURRENT opaque receipt/route/verifier/app key+nonce/ciphertext/timing, **not default source locator/height/value**. | Same receiver/note necessary; stable app keys, sidechannels or matcher-accessible private maps may still join note→order. Historical preSep30 cmx-derived/default-value wire rejected. | Optional diagnostic off by default; funded money critical path disabled even if message delivery works. |

**Privacy boundary test rule:** make an explicit access graph of legal control, cloud admin, shared logs, support tickets, telemetry and data exports. Grant the attacking matcher *all* reachable sources. Test order-content extraction **and separately** order-to-identity mapping on accepted orders; a failed join in a restricted, fictional view cannot justify the claim. Independent custodians/eligibility actors may legitimately know identities/payment details, but if a matcher can access them they belong in its attack view. [I]

## 4. Invariants and state/failure ledger [I; all prospective]

| ID | Required invariant and invalid transition | Evidence test |
|---|---|---|
| I01 — privacy | No one matcher/control domain recovers plaintext order fields **or** joins an accepted order to a participant. No funded matching while ingress/funding linkage design or evidence is absent. Public and privileged-custodian leakage disclosed separately. | T01–T03 |
| I02 — exact domain | Client signature, ciphertext/admission/funding proof, sealed fill and custody authorization bind Solana cluster, Zcash network/Ironwood pool, exact pair/mint/program, epoch/rules hash, expiry, maximum amount and one-use nonce; wrong or stale domain rejects without asset effects. | T03, T05, T06 |
| I03 — funded set and symmetric holds | Scanner (not Zoss) confirms unique claimant-bound controlled ZEC credit; FAA prepares buyer **FULL max debit** or seller atoms before accepted root/certificate. Prepared→EpochEncumbered after finalized canonical COMMIT; lost ack/zero Fill records/expiry/slow MPC/restart cannot refund/reassign. Every portion exclusive, disjoint portions may coexist. Only final allocation or definitive canonical irreversible ABORT/exclusion with stale-commit/authorization fences safely releases. | T03–T05, T10; parent PD01–PD03 |
| I04 — accepted set/rules | All receipts in independently available, non-equivocated accepted ciphertext set enter computation; rule/version and exact set root match final sealed allocations. Missing inputs, invalid circuit and selectively aborted execution do **not** produce executable results. Pre-acceptance censorship is detectable only insofar as receipt policy specifies; it is not erased by MPC. | T04, T07–T08 |
| I05 — bounded clearing/private output | Checked raw integer amounts/limits/max debit, equal filled sides, no funding overrun. Later candidate fixed8 zero-fee auction and authenticated private permutation fixed before root commit; no public exact price/per-order mapping default. Historical D0 researcher price/tie-key demonstration is separate. Active output/public auxiliary inference still hard privacy gate. | T08–T09; parent PD07,PD13 |
| I06 — unique two-ledger release | Each uniquely reserved *entitlement unit* of a trade+leg has at most one terminal release or refund; filled ZEC payout and unused buyer-credit refund are **disjoint portions**, not competing claims on the same zatoshis. Bind distinct nonces, prior→next state, exact recipient/amount/expiry/roster/quorum version. An already-sent opposite leg constrains later refund eligibility; quorum truthfulness is a distinct trust assumption. | T05–T06, T10–T13 |
| I07 — finality and conservation | For unique confirmed buyer C, `C = available + admission_prepared + epoch_encumbered + seller_payout_outstanding + buyer_unused_outstanding + seller_payout_final + buyer_refund_final`; seller locked total analogously partitions available/locked, prepared, epoch-encumbered, filled outstanding, final unfilled returnable, released, returned. All disjoint; pending spends outstanding, change/in-flight inventory counted once, not new credit; zero candidate protocol fee/sponsor fees separate. Reorg/impairment pauses/reconciles without phantom availability. Complete needs both final legs and reconciled claims. | T09–T13; parent PD01–PD03,PD12 |
| I08 — fail closed/fenced recovery | Unknown chain/journal/commit/allocation/intent state keeps buyer max debit AND seller atoms held. Preallocation release only definitive finalized irreversible canonical ABORT/exclusion plus stale-commit/authorization fences. ReserveFill is NOT Release authority: durable FirstLegPrepared+canonical fence precedes live Release signatures. No ordinary abort once authorized/sent/ambiguous. Safe filled cancel only finalized mutually exclusive cancel_fill/release_spl state with SPL unreleased AND all signer journals showing no native payout intent/signature/broadcast; otherwise Disputed. ZEC quorum/inventory dependent, SPL issuer dependent, no negative Zcash proof. | T10–T15; parent PD01,PD06,PD10 |

Proposed pre-match hold and per-trade state diagram, not implementation evidence:

```text
Available own-leg credit/locked atoms
  -> AdmissionPrepared (FULL buyer max debit / seller atoms; generation fence)
  -> finalized canonical COMMIT -> EpochEncumbered (matching delay never frees)
  -> authenticated allocation + canonical finalized FINAL + SAME journal activation
  -> disjoint FilledOutstanding / FinalUnusedReturnable
Prepared/Encumbered -> safe release ONLY canonical irreversible ABORT/exclusion + fences
FilledOutstanding -> Authorized -> SPLSent/Final -> ZECSent/Final -> Complete
Live Release requires prior durable FirstLegPrepared + finalized canonical first-leg fence
Ordinary abort forbidden; safe fill cancel only finalized Cancelled/no SPL + no native intents
```

Later candidate selects **SPL-first**, one concurrent fill: seller may lose SPL if ZEC quorum withholds/misdirects or payout reorgs. ZEC-first historical comparison exposes buyer if SPL freezes; not automatic fallback. No first leg until finalized canonical FINAL and private journal activation agree. 2-of-3 spends do not serialize business history: candidate uses unanimous three-domain decision acknowledgements, one fenced writer and durable intents, sacrificing liveness; corrupt spend threshold can still steal. Timeout neither recalls a paid leg nor proves absence of future spend. Near-expiry/ambiguous broadcast retains exposure and disputes; no Complete until both final effects+claims reconciled, no guaranteed resolution/compensation. [I]
