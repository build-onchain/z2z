# Optional node transport identity — approved P2.02 design

**Date:** 2026-10-06. **Status:** OWNER-APPROVED WRITTEN DESIGN. The owner explicitly approved this exact design and52-byte format on2026-10-06. Approval permits the narrow implementation plan; implementation remains held until that plan is reviewed/approved. This is the next narrow transport wave, not financial identity, recovery, trading or P0.07 network implementation.

## Intent and chosen boundary

An owner explicitly opting in can restart `z2z-node` with the same transport PeerId; omission preserves today's ephemeral flow with no key-file access or creation. Add `peer_identity_file: Option<PathBuf>` to existing node Options/strict schema-version-1 JSON/Config, exposed as `--peer-identity-file PATH`; include it in the existing `--config` versus transport-flags conflict. The JSON holds only the path, never key bytes. Resolve a relative path against startup cwd once. Require an existing owner-private directory **outside the checkout, target and build-output trees**; do not create a directory, chmod an existing entry, search default locations or load a wallet. Missing option means ephemeral, not an implicit default file.

Use one independently generated Ed25519 transport secret, not an owner seed, spend/recovery key, consent key or session coordination key. Existing configured expected PeerIds continue to authenticate remote Noise handshakes. A persistent PeerId is not wallet ownership, backed liquidity, financial authorization or anonymity. This wave stays TCP/Noise/yamux with existing discovery/reconnect settings; it enables none of QUIC, gossip, sessions, LAN/WAN, signing/proving, SQL or funds.

**Selected approach:** a small fixed plaintext transport-secret file with existing custody filesystem mechanics. Compared with always-ephemeral identity, it permits configured-peer restart without re-exchanging an address. Encrypted custody envelopes would require another unlock secret and financial-envelope coupling without protecting an already compromised owner process; they are not selected. **Risk:** anyone able to read the file can impersonate the transport PeerId; disk snapshots/backups/root/same-UID compromise remain threats. No at-rest encryption, secure-deletion, whole-process zeroization or unlinkability claim.

## Exact file format and secret handling

Exactly **52 bytes**, no padding, length prefix, serde, JSON, base64, public-key copy or checksum:

```
ASCII "Z2Z_PEER_IDENTITY\0" [18 bytes]
|| u16BE(1) [2 bytes]
|| Ed25519 secret seed [32 bytes]
```

Require exact domain/version/length and EOF; unknown versions, short files, extra bytes and legacy raw32/raw64 encodings reject. This domain is distinct from every financial/custody format. Derive public key/PeerId from the seed rather than trust a stored public-key field. A format header detects wrong-file use, not malicious replacement by the trusted same UID; any32 seed bytes are a valid Ed25519 seed, so no fictional cryptographic corruption check.

Read into fixed `Zeroizing<[u8;52]>` plus a guarded one-byte EOF probe, with metadata size checked first and metadata revalidated after reading. Generate directly into the guarded seed slice using the already installed fallible OS-randomness facility; entropy failure aborts. Do not serialize `Keypair::to_bytes()` (64 bytes), call `secret()` for unnecessary copies, or create an unguarded secret Vec/String. After publication/readback, `ed25519::SecretKey::try_from_bytes(&mut frame[20..52])` consumes/zeroes the seed slice on success; promote to the existing libp2p keypair and pass it to `SwarmBuilder::with_existing_identity`. Keep guards on failure too. The live libp2p key necessarily remains in memory for transport authentication; upstream internal copies are not an erasure guarantee. No secret Debug/serde/event/error, file content/hash, path logging or secret-bearing command argument.

## Filesystem admission and publication

Reuse the descriptor-relative custody trust/open/locking/fsync/NOREPLACE mechanics, **not** `save_encrypted` or its interrupted-encrypted-envelope repair semantics. Keep the shared Linux primitives in existing custody ownership with only the narrow crate-private access needed by node identity; no universal storage API/new crate and no `sp1-local` requirement. The current trusted backup-key helpers are feature-gated and raw32-specific, so using them unchanged is incorrect.

1. Before listening/dialing or constructing a Swarm, resolve and validate the path component-by-component. Reject `..`, symlinks, dot-prefixed final basenames and paths inside the checkout/build trees. Walk with descriptor-relative `NOFOLLOW|DIRECTORY|CLOEXEC|NONBLOCK`; no `canonicalize`-then-open trust gap. Immediate parent must belong to effective UID with exact0700. Ancestors must belong to root/effective UID and not be group/other writable, except the existing exact root-owned sticky01777 ancestor policy (for example `/tmp`). Validate an existing parent only, never provision it.
2. Acquire the existing **directory-wide exclusive publication flock** before inspecting final/stage or generating a key. Use nonblocking attempts with a5s monotonic startup deadline (10ms retry interval, no worker/task per retry); lock contention timeout is a categorical failure, not ephemeral fallback. Revalidate the locked directory. No sidecar lock file; release on every return. Both cooperative simultaneous startups serialize on the same directory inode.
3. If final exists, open `RDONLY|NOFOLLOW|CLOEXEC|NONBLOCK`, require regular file, effective-UID owner, one hard link and exact0600 (including special-bit rejection). Take a shared file flock while reading; validation/lock/fsync errors abort. Read/validate the52-byte format, sync file and parent, then use only these bytes. Do not inspect, delete or repair a leftover stage when a valid final already exists. Never truncate/replace/remove the final, including after an indeterminate earlier fsync.
4. If final is absent, inspect the reserved stage `.<basename>.pending` under the same parent lock and secure file rules. A complete valid stage is the interrupted publication's chosen key: sync it and resume its publication. Any malformed/unknown/partial/unsafe stage aborts **without repair/deletion or new key generation**. Unlike encrypted custody, even a recognizable interrupted identity stage is not automatically removed.
5. Only if both names are absent, generate the guarded frame and create the stage via descriptor-relative `CREATE|EXCL|WRONLY|NOFOLLOW|CLOEXEC|NONBLOCK`, mode0600. Revalidate metadata; restrictive umask causing a different mode rejects, never chmods. Take an exclusive file flock for writing, write exactly52 bytes, `fsync(stage)`, then `renameat_with(..., NOREPLACE)` and `fsync(parent)`. Failed writes/syncs leave the stage/final untouched for explicit diagnosis; no deletion, overwrite or new-key fallback. Do not hold the stage lock while reopening the renamed inode for the shared read lock.
6. **Always reopen and validate the winning final**, with shared file lock/readback/file+parent fsync, before deriving the key used by Swarm. NOREPLACE `EEXIST` means discard only the in-memory candidate and validate/use the winner; never overwrite it, compare its secret in logs or continue with the losing generated key. Leave any losing stage untouched. Other rename or durability errors stop startup. Two valid concurrent startups that complete must report the **same winning PeerId**; a contender that hits lock/I/O policy fails explicitly, never starts a different identity. Reuse the final on every subsequent restart; no automatic key rotation.

Descriptor and advisory-lock discipline protects against other users and cooperating publishers, not malicious root/same-UID mutation. Revalidate file metadata around readback; a malicious trusted actor can still replace a valid key. Rotating/removing a transport key is an explicit external owner operation outside this wave, not a financial recovery action.

Use existing [node transport process suite](../../../crates/runtime/tests/node_transport_cli.rs), [reconnect suite](../../../crates/runtime/tests/node_reconnect_cli.rs) and custody unit-test conventions, generated transport keys and private0700 temporary roots only:
