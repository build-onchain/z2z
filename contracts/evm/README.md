## Implemented samechain boundary

The constructor fixes one token address/code hash, nonzero owner-program VKey and chain ID, internally constructs `new SP1Verifier()` from the actual vendored code (no injected verifier/gateway), pins its runtime hash and initializes the depth-32 tree. The deployment descriptor binds actual post-construction authority/verifier addresses and runtime hashes, chain, owner program and schema. A constructor-supplied VKey is **not** an independently trusted financial profile; vanilla non-proxy/non-rebasing token semantics, artifact/setup provenance and the actual owner program still require qualification. There is no admin sweep, upgrade, root publisher or company-only spend allowlist in this source.

All four mutators reconstruct canonical expected journals from strictly decoded packets and call the actual verifier under the fixed `ownerProgram`; wrapped bytes must be exactly356 bytes (selector plus exit/VK-root/nonce/eight pairing elements):

- `create(rawPacket, proof)` authenticates `msg.sender` as the declared payer, exact Native `msg.value` or zero token-call value, fixed-token/asset identity and signed expiry. After proof acceptance, token receipt requires exact payer-decrease **and** authority-increase deltas. Payer-scoped creation nonces and optional initial order IDs are reserved; initial IDs remain reserved after cancellation/exit. Receipt, reservation and backed append are one transaction.
- `fill(rawPacket, proofA, proofB)` checks both retained root counts and `index < count`, global deployment-scoped unspent nullifiers, then verifies both Fill2 owner journals binding the same complete packet and ordered-leaf aggregate C before either consumption/output. `SamechainCodec` expects relation2 only for Fill, relation1 for Cancel/Exit and unchanged outer journal frame/length; ownership, dual consent, conservation and successors belong to the pinned guest.
  Current V1 requires both owners online and fresh exact consent; one-opening-signature/offline-standing multi-fill remains V2, not delivered by this cutover.
- `cancelOrExit(rawPacket, role, action, proof)` accepts only role A/B and Cancel/Exit, verifies the single order-owner journal, consumes the same generation nullifier used by Fill and applies authorized outputs. This invalidates all F1/F2 packets for that backing generation, not just one digest.
- `withdraw(rawPacket, proof)` verifies the distinct ordinary-note withdrawal journal, consumes its nullifier and applies the exact Exit/Fee/change manifest; no fabricated order metadata is required.

Output commitments are deployment-globally unique (`seenCommitments`), including across rollover. Every successful note append retains its intermediate `(treeId, root) → count`; empty initialization/rollover roots are not spend-admitted. SHA256 leaves bind deployment/tree/index/commitment, count uses `u64` through `2^32`, and full-only rollover rejects tree-ID exhaustion. The ordered manifest publishes complete note ciphertext/version/recovery commitment and insertion metadata, or executes the exact Native/fixed-token payment. Token sends require exact authority-decrease and recipient-increase deltas with strict balance/return decoding. Reentrancy/identity guards and EVM reverts cover verification, nullifiers, nonce/ID/commitment/root state, every ordered output and all transfers atomically; a publication or receiver/token failure cannot leave a partial transition. These are implemented control paths, not exercised funded-success claims.
